## The work
1. **Inventory the shared state** first (report section 1, before any code): every cache, static, global, and Qt object touched during a bake, and whether it is read-only after a warm-up, written per chunk, or written per texel. Reads that race are the only bugs this lane can create; list them before touching anything.
2. **Chunks and tiles in parallel**: terrain chunks, object chunks, pyramid tiles, native emission per chunk over `QThreadPool` / `QtConcurrent` with the shared caches made read-only before the fan-out (warm them on the main thread: the LTEX/TXST/GRAS resolution, the model loads for the region's base set, the texture decodes) and per-worker scratch for the rest; the GUI's chunk-per-tick becomes N in flight per tick with the same cancel semantics between chunks; the live preview updates as results land in DETERMINISTIC order (results are queued by chunk index, not by completion). ORDER-SENSITIVE OUTPUTS (manifests, the `.lodi` sort law, the `.lodo` table sort laws, texture-array layer assignment, card-array packing) must be produced from the deterministic queue, never from completion order.
3. **BC encoding per block row in parallel** (embarrassingly parallel; a row of 4x4 blocks per task).
4. **Card bakes batched**: the impostor bake hook renders K models per frame into offscreen targets under the one-instance rule (state K and why); the driver `tools/bake_impostor_cards.sh` loses its one-model-per-launch loop where it can. If the hook cannot batch without changing the picture, refuse with numbers.
5. **Writes off the critical path**: file writes on a writer thread with a bounded queue; the run ends only when the queue drains (a run that exits 0 with a file still unwritten is worse than a slow run).
6. **The gates**: (a) WHOLE-REGION BYTE IDENTITY, single-thread vs multi-thread, every output file, on both test regions, with `--threads 1` as the exact way back (a new switch and a panel row are NOT this lane's to add -- the switch yes, the row is LODUI1's or a follow-up; say so); (b) the four stage times before/after on both regions (the instrument LODUI1 shipped), printed as a table with the speed-up per stage; (c) a `threads` census word written and moving; (d) peak working set printed (Windows job object or `GetProcessMemoryInfo`) so 31 GB is never exceeded on the Commonwealth (extrapolate from the 25-chunk region and STATE the extrapolation); (e) the run with `--threads 1` on the new exe is byte-identical to the rung exe's run (the parallel rewrite changed no arithmetic).

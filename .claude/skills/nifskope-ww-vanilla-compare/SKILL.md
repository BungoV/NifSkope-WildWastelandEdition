# NifSkope WW: vanilla vs ours, in one picture

Repo `E:\Projects\NifskopeWildWastelandEdition`. Read `CONSTITUTION.md` first
(rule 4 measurement, rule 5 proof by picture). The rendering mechanics —
`WW_RENDER_*`, `WW_WINDOW_AT`, one instance, an unused `--port` — live in
`nifskope-ww-render-shot`; the generator CLI lives in `nifskope-ww-lodgen`.
This skill is only the comparison: choosing the subject, serving both sides,
pinning one camera, and the traps.

## 0. Gates before the exe runs

```bash
tasklist | grep -iE "Fallout4.exe|NifSkope.exe"     # both must be absent
ls -l release/NifSkope.exe                          # newer than every src/ file
```

Put both gates in the driver script, not in your head — the game can come up
mid-lane. A driver that refuses is a result; a render taken beside a running
game is not.

**Every path handed to `release/NifSkope.exe` is ABSOLUTE.** The exe resolves a
relative `--out-dir` / `--tex-dir` against its OWN directory, not the shell's
cwd, so a relative path writes into `release/`. Cost one round, 2026-09-09.
List the file on disk before believing the run's own "written to …" line.

## 1. Choose the subject from the MASTER only

Never rank candidates on anything we generated — that is circular, and bungo
has caught it once ("we do that check on the vanilla map. Not the new generated
one we have"). Score vanilla's shipped files and say why the winner won.

For far terrain the two numbers that matter, both on the shipped sheets in
`E:\Tools\Fallout 4\DataUnpacked\Data\Textures\Terrain\<ws>` at mip 2, decoded
with `scratchpad/mountains_20260907/dds.py` + `bcnp.py`:

* `colour` = mean of `max(RGB) − min(RGB)`. A blank or grey tile scores ~0.
* `relief` = mean angle of the `_msn` normal away from up, in degrees.
  **Up is GREEN in FO4's terrain `_msn`**, not blue.

Rank by `colour × relief`, print the whole table, quote the winner and the
last row so the spread is visible. `pick_region.py` in that folder is the
working version (takes a dim and an optional cell box).

The Commonwealth painted box is **x −36..32, y −41..32**; everything else has
height but no painted material. "Outside the playable area" means a tile whose
whole cell block misses that box.

To name a summit inside a cell rectangle, use the ESM, one call a cell:

```bash
release/NifSkope.exe -no-gui lodgen "<Fallout4.esm>" --worldspace 3C --cell X Y
# -> cell (-60,36) LAND corners  SW … NW …  center 38840
```

A cell whose `center` beats all four of its own corners is a summit, not a
shoulder. Do NOT reach for the FO4CS worldspace heightmap DDS instead unless
you first cross-check its decode against three known ESM cells: the obvious
"R16 linear over the name's range" reading disagrees with the ESM by thousands
of units (2026-09-09).

## 1a. Pick the tile by PROJECTING the thing under test (2026-09-11, lane ROADS1)

Step 1 says: rank candidates on vanilla's own files. This says the other half:
**when the comparison is about a THING — roads, rubble, a building family, a
water body — rank the candidates by where that thing actually IS, and never
inherit a tile from the lane before you.**

Lane ROADS1's brief pointed at lane TERRAIN-R's picture of chunk (-20,24) and at
its sentence *"most of it is the roads ... vanilla carries and we do not"*.
Chunk (-20,24) contains **zero road triangles**. The Sanctuary loop road is one
chunk SOUTH. Four lines found it, before any measurement was believed:

```python
# every placement of the family, projected onto the dim-4 chunk grid
c = collections.Counter()
for p in placements_of_the_family:
    for s in model_shapes(p):
        v = world_space(s, p)
        for cx in range(floor(v.x.min()/4096), floor(v.x.max()/4096) + 1):
            for cy in range(floor(v.y.min()/4096), floor(v.y.max()/4096) + 1):
                c[((cx // 4) * 4, (cy // 4) * 4)] += len(s.triangles)
# -> (-16,16) 284532   (-20,20) 86770   (-16,24) 63703   (-20,24) 0
```

The bounding box is enough; the point is which chunk, not which texel. Do it
BEFORE choosing the fixture, and print the whole histogram in the report, so the
choice is a measurement and the rejected candidates are visible.

**The failure it prevents is not "a worse tile" — it is a FALSE CAUSE.** A tile
with none of the thing in it will still show a difference against vanilla (ours
did: mean 19.96 of 255), and that difference will be attributed to the thing
because that is what the lane was looking for. Projecting first is what keeps
"most of it is the roads" from becoming a fact by repetition.

## 2. Serve OUR files to the renderer without touching the game data

`NifModel::load` calls `getNIFDataPath()` on the file it is opening and hands
the result to `addNIFResourcePath` (`src/model/nifmodel.cpp:2147`). For a
`.nif` / `.bto` / `.btr` that is **the folder the file sits in**, and
`GameResources::find_file` (`src/gamemanager.cpp`) searches it BEFORE the
game's archives. So stage each side as its own miniature data root:

```
<side>/<Chunk>.BTR
<side>/textures/terrain/<worldspace>/<Chunk>.DDS
<side>/textures/terrain/<worldspace>/<Chunk>_msn.DDS
```

because the chunk names its textures `Data\Textures\Terrain\<ws>\…` and
`get_full_path` reduces that to `textures/terrain/<ws>/…`. Copy vanilla's
`.btr` + its sheets into one folder, put ours in another, render both. Nothing
in the game folder is written, and neither side can borrow the other's files.

**Prove the staging works before you trust the picture.** Decode both sheets
first and know what each side MUST look like — e.g. our far diffuse is a flat
grey at luminance SD 0.00 while vanilla's is 14–16. If our half comes back
carrying vanilla's colour, the override failed; if it comes back white, the
texture was not found at all. Two different failure colours, both distinct
from the expected answer.

To isolate sheets from mesh, stage a third folder: vanilla's `.btr` with OUR
sheets beside it. Same mesh, same material, only the textures differ.

## 2a. Read VANILLA as loose files, or you may be comparing with yourself

The worst outcome of a vanilla comparison is not a wrong number. It is a number
that agrees with itself perfectly and means nothing, because "vanilla" was our own
previously installed output.

Any read that goes through the resource stack -- the game's `Data`, an MO2 virtual
tree, a BSA plus loose overrides -- resolves by LOAD ORDER, and our generated mod
is in that order. A bake that "reuses vanilla", a script that measures "vanilla's
sheet", a picture labelled VANILLA: each will silently pick up yesterday's run the
moment the output mod is enabled, and every statistic then reads as a spectacular
match.

**The rule: vanilla is a PATH, not a stack.**

- Read from an unpacked vanilla tree by absolute path (`E:\Tools\Fallout 4\DataUnpacked\Data`),
  never through the resource system, and make the root an explicit argument
  (`--vanilla-lod-root`) so a reader can see which tree answered.
- Validate what came back before using it -- length and magic bytes at minimum. A
  missing file that returns empty is better than a wrong file that returns.
- Make the code SAY what it did: a census counter for "reused" against "made our
  own". Lane TILING3 shipped `msnCopied` / `msnOurs` / `colCopied` / `colOurs` in
  the run's own report line, so a bake that quietly found nothing announces it
  instead of looking successful.
- Before believing a strong vanilla-vs-ours agreement, ask once: **could this file
  be ours?** Then prove it cannot be, by pointing the root at an empty directory and
  showing the result changes.

The same trap in its measurement form: a "vanilla" statistic computed from a sheet
our own bake installed is the phase-twin floor's opposite -- a ceiling of 1.000 that
is an artefact of provenance. Cost zero this time only because the root was made
explicit before the first read.

## 3. Pin ONE camera across both halves

Auto-fit frames each file by its own bounding sphere, and ours is rarely the
same as vanilla's (measured: identical at dim 4, 1702 vs 1646 centre and 2987
vs 2943 radius at dim 16). So set the camera explicitly:

```
WW_RENDER_VIEW=8                 # ViewUser, the oblique startup view — the only
                                 # non-axis-aligned view the hook can select
WW_RENDER_CENTER=x,y,z           # scene units
WW_RENDER_DIST=<units>
WW_RENDER_SIZE=1400x900          # the window may resolve this to something else
                                 # (1507x841 here) — that is fine, both halves
                                 # get the same, but read the real size back
```

Scene units for a terrain chunk: the chunk spans `dim × 4096` on x and y from
the origin, so its centre is `dim × 2048`. Read z from the
`BSMultiBoundAABB`'s `Position` (`-no-gui dump <file> -b 5`). A close-up on a
feature takes that feature's own world position as the centre.

**The camera pin is verified, never assumed** — render the same file at two
distances and show two different files. `nifskope-ww-render-shot` says so; do
it and put both control frames in the folder.

## 4. The two things that put the WRONG difference in the picture

1. **Vertex colours.** `lgTerrainIdentity` defaults to **true**
   (`src/nifcli.cpp:5144`), so our terrain chunks carry the FO4CS channel
   contract in `Vertex Colors` and vanilla's carry no such field at all. The
   renderer multiplies it into the diffuse and our half photographs deep blue.
   Pass **`--no-terrain-identity`** for a like-for-like picture, and check the
   two files agree:
   ```bash
   release/NifSkope.exe -no-gui get <file>.BTR -b 1 -f "Vertex Desc"
   release/NifSkope.exe -no-gui get <file>.BTR -b 1 -f "Vertex Data/0/Vertex Colors"
   ```
   Vanilla Commonwealth terrain is `Vertex Desc` 52776558133763 with no
   `Vertex Colors` field; ours must match that number before you shoot.
   (`--no-identity` is the equivalent for `--objects`.)
2. **Shader constants.** `dump -b 2` both sides. Ours has shipped Smoothness 1
   / Specular #000000 / Clamp 3 against vanilla's Smoothness 0 / Specular
   #ffffff / Clamp 0. That is a real difference in our output, so leave it in —
   but SAY it is in the frame, or the picture gets read as a texture result.

Same shape of question for any asset: list what differs between the two files
besides the thing under test, and either neutralise it or name it in the
caption.

## 5. Compose it so it cannot be misread

* Two halves, **the same crop box applied to both**, nothing scaled.
* `vanilla` / `ours` burned into the image, not in the filename.
* A hairline between the halves so they do not read as one picture.
* A caption naming the tile, the cells, the camera and the exact generator
  command, so the picture regenerates from the picture.
* `compose.py` in `scratchpad/mountains_20260907/images/` does all of it
  (Pillow 10 is installed); it splits the caption on `|` into lines and, since
  2026-09-09, WRAPS each line on the measured text width. Before that fix a
  caption line wider than the picture ran off the right edge and lost its own
  tail — including the line that disclosed the material difference. **Open the
  composed PNG and read it.** A compositor reports that it wrote a file, never
  that the file says what you passed in.

Deliverables go under `scratchpad/<topic>_<date>/`, never only in `%TEMP%`
(CONSTITUTION 8), and the report names the cell, tile, camera and commands.

## 6. What a comparison picture may NOT say

It may not carry a verdict on the cause. Two sentences on what is visibly
different, then the numbers that were measured and the ones that were not.
"Fixed", "final" and "true" wait for bungo (CONSTITUTION 9).

## 7. Take a texture OUT of the comparison (normal-only, albedo-only, …)

bungo asks for this the moment two halves differ in more than one way: *"show
me the vanilla normal map on the left, without the diffuse"* (2026-09-09).

**There is no normal-only lit view in the render hook, and there is no switch
that turns one texture slot off.** Checked in source, not assumed: the hook's
switches are `WW_RENDER_SHOT/SIZE/VIEW/TIME/FLAT/CENTER/DIST/REFRACTION/SEQ/SS`
plus `WW_LOD_CHANNEL` (`src/nifskope_ui.cpp` ~21251-21410), and the channels are
`1..13` in `res/shaders/fo4_default.frag` (~267-345). Channel **8 is the
GEOMETRIC normal** — `normalize(btnMatrix_norm[2])`, the interpolated vertex
normal — not the sheet; channel 10 is the gloss/specular channel; and
`WW_RENDER_FLAT=1` kills the normal map along with everything else.

So you do not switch the slot off, you **substitute a sheet that carries no
information**, byte-identical on both halves, and let the lit path run
untouched.

### The constant sheet

BC1, the tile's own size, the full mip chain, every block
`colour0 = 0x8410`, `colour1 = 0x0000`, all four index bytes 0 — `colour0 >
colour1` is the 4-colour opaque mode and index 0 selects `colour0`, so every
texel of every mip is exactly that colour. `0x8410` decodes to **(132, 130,
132)**, the nearest 565 value to 128 grey. Copy the 128-byte header from a sheet
the renderer already accepts instead of hand-writing one, and regenerate the
payload in full.

`scratchpad/mountains_20260907/images/make_grey.py` is the working version:

```bash
python images/make_grey.py <abs donor 512x512 DXT1 .DDS> <abs images/flat_grey.DDS>
# -> 512x512  8 mips  174888 bytes
```

Prove it is constant before you use it — `dds.py` + `bcnp.py`, several mips,
**min == max per channel**. A sheet you believe is flat and is not puts a
texture back in the picture under a name that says it is gone.

### The three controls, all pre-registered

1. **Noise floor: render one side twice.** These renders are deterministic —
   two independent runs of the same staged folder came back **byte-identical**
   (mean abs difference 0.000000, 2026-09-09). Establish that first, or you
   cannot say any later number is real.
2. **Neutrality where it must hold.** Pick the side whose real sheet already
   equals the substitute and show the substitution changed *nothing* there. Our
   far-terrain diffuse is already this exact flat grey, so
   `shot_nrm_ours16.png` came back byte-identical to the earlier
   `shot_ours16.png`, while vanilla's half *did* change. Two facts in one
   control: the substitution is inert, and the staging is really serving our
   folder.
3. **A fourth staged folder that isolates the sheet.** Vanilla's `.btr`,
   vanilla's material, the grey diffuse, and only the `_msn` swapped for ours.
   Measured over the terrain pixels inside the delivered crop: sheet-only
   **12.198** mean abs difference against a **0.000** floor, where the delivered
   pair (different mesh *and* material *and* sheet) was **20.280**. That single
   number is what stops the picture being read as a texture result when the
   materials also differ.

Check `dump -b 3` on both chunks before you claim which slots are in play — FO4
terrain LOD names only slot 0 (diffuse) and slot 1 (`_msn`), so `hasSpecularMap`
is false and the `_data.DDS` our generator also writes is never bound.

### What a `_msn` picture can and cannot mean here

The lit path **discards the stored blue** and recomputes it,
`normal.b = sqrt(max(1 - dot(normal.rg, normal.rg), 0))`, then multiplies by
`btnMatrix_norm` — it treats FO4's MODEL-space terrain sheet as a tangent-space
one. Two sheets differing only in blue render identically. Say so beside any
raw-sheet crop, which does show blue.

### The raw sheet beside the render

Give him the bytes as well as the shading: `msn_crop.py` decodes the DDS,
takes the **same centred texel region of the same mip** from both files, and
scales it nearest-neighbour so one screen block is one texel.

```bash
python images/msn_crop.py <abs _msn .DDS> <abs out.png> 0 160 4    # mip 0, 160x160 texels, x4
```

Quote per-channel SD and the **distinct-colour count over the same texel
count** — that is the number that carries "ours is interpolated between far
fewer values" (2,160 against vanilla's 4,919 in 25,600 texels, dim 4,
2026-09-09). Do not label a texel with a cell unless the sheet-to-cell mapping
has been calibrated against the ESM; centre both crops and say that is what
they are.
